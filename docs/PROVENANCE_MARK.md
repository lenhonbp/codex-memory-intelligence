# CMI Provenance Mark

## Purpose and term

The **CMI Provenance Mark** is a compact, user-visible statement that Codex Memory Intelligence participated in a workflow and, when the evidence supports it, durable Session evidence was recorded. It communicates product identity plus evidence provenance. It does not claim that CMI authored the source code.

Use the term **CMI Provenance Mark**. Do not describe the mark as a signature, certification, approval, authentication, or verification mechanism. Do not say that work was “Generated by CMI”, “Written by CMI”, “Signed by CMI”, “Authenticated by CMI”, “Certified by CMI”, “Approved by CMI”, or “Verified by CMI”.

## User-visible form

For substantial work, place the mark after the normal answer and any evidence-backed `### CMI Intelligence` section.

Use the evidence-backed form only after a real durable CMI Session was successfully created and finalized:

```markdown
### CMI Provenance

**CMI-assisted workflow** · Durable session evidence recorded by Codex Memory Intelligence

- Session: `<actual-session-id>`
- Change: `<actual-change-id>`
```

The Session value must be the actual observed identifier of the finalized Session. Include the Change line only when an actual associated Change record exists and its identifier was observed. Never synthesize, shorten into an ambiguous value, or infer either identifier.

When the managed CMI operating contract applied but no durable Session was recorded, use this explicit degraded form:

```markdown
### CMI Provenance

**CMI operating contract applied**

- Durable CMI evidence: not recorded
```

If a Session was attempted but its lifecycle or finalization was unavailable, the last line may instead say `CMI session evidence: unavailable`. Choose wording that states the observed condition. A failed or incomplete lifecycle must never be presented as having durable session evidence recorded by CMI.

The mark is a provenance footer, not a second completion report. Do not repeat the alerts or verification details already presented under `### CMI Intelligence`.

## Pull request form

When creating or updating a pull request is already authorized, place the same truthful mark inside one bounded block:

```markdown
<!-- cmi-provenance:start -->
### CMI Provenance

**CMI-assisted workflow** · Durable session evidence recorded by Codex Memory Intelligence

- Session: `<actual-session-id>`
- Change: `<actual-change-id>`

<!-- cmi-provenance:end -->
```

Omit the Change line when no actual Change exists. Use the degraded wording instead of the evidence-tracked wording when no finalized durable Session exists. On a later PR update, replace the content from the single start marker through the single end marker; never append a second block. The markers and field order are deterministic so the block is bounded, idempotent, replaceable, and non-duplicating.

The mark never creates authority for an external action. Do not create or update a PR solely to add CMI identity. CMI does not automatically mutate GitHub or another external system for this feature.

## Trust boundaries

- **Authorship:** CMI may orchestrate context, Session, Change, verification evidence, Closing Intelligence, and agent workflow. That does not make CMI the author of project source. Do not add watermark comments to source files or alter copyright/license headers.
- **Authentication:** The mark is not a cryptographic signature and does not authenticate a person, agent, repository, commit, or artifact.
- **Portable Evidence:** The mark does not change Portable Evidence identity or integrity semantics. `identity.digest` and `integrity.digest` remain integrity mechanisms, not authorship or authentication, and `authenticated: false` remains unchanged.
- **Operational Trust:** A clean `cmi-trust` result remains a sharing guardrail. It does not make the mark “verified”, “certified”, “trusted”, or “authenticated”.
- **Evidence Contract:** The mark is an agent integration/presentation convention. It does not change protected Finding, recommendation, verification, evidence-address, or `violationEstablished` semantics and does not require an Evidence Contract version change.
- **Git metadata:** Provenance Mark v1 does not add commit trailers or silently change commit-message conventions.
- **Brand policy:** The mark must remain truthful about CMI participation and must not imply endorsement of an independent fork or approval of another product.

## Future possibilities

Cryptographic signing, authenticated identity, opt-in Git trailers, or first-class PR integrations require separate designs, trust models, compatibility review, and explicit authorization. They are not part of Provenance Mark v1.
